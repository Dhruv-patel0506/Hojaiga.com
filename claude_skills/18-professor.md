# Skill 18 - Professor (see the screen, teach the app, point at the buttons)

Clicky's idea (a voice companion that sees your screen and flies a pointer to what it talks about), rebuilt for Windows, local models and Hojaiga's laws.
Entry: `All codes/core_organs/hojaiga_professor.py` (package `core_organs/professor/`). Tests: `si_tests_professor.py` (PR1-PR39 offline, PL1-PL11 + PV1/PV2 live).

```
python hojaiga_professor.py catalog [--hwnd N|--title T] [--save] [--json]                                    Verb Registry + Shortcut Map from the app's own menus/tree (passive)
python hojaiga_professor.py archetype [--hwnd N|--title T|--image F]                                          what KIND of software, where properties / structure live
python hojaiga_professor.py probe  [--hwnd N|--title T] [--allow-input --authorize]                           learn how it behaves (safe verbs only; DRY RUN unless both flags)
python hojaiga_professor.py exec   "<goal>" [--hwnd N|--title T] [--run --allow-input --authorize]            plan with the app's own commands; hotkeys over pixels
python hojaiga_professor.py scan   [--hwnd N|--title T|--image F] [--mode quick|standard|deep] [--json]     every control, regions, coverage proof
python hojaiga_professor.py ask    "<question>" [--mute] [--no-overlay] [--auto]                             look -> plan -> speak + point -> watch you
python hojaiga_professor.py here                                                                              what is the control under my mouse?
python hojaiga_professor.py listen                                                                            hold Ctrl+Alt, talk, release (Esc cancels)
python hojaiga_professor.py server status|start|stop|tune                                                    local Qwen3-VL (llama.cpp), hidden, 127.0.0.1:8081
```

## The pivot (why this exists)
Reverse-engineering compiled code to learn how to USE an app is brittle. People learn by LOOKING. So: capture the pixels, find the controls, name them, and
explain them from measured knowledge; code (repo graph) is an optional second witness, not the foundation.

## Pipeline - each stage reports what it skipped (law L2), nothing is faked
| stage | module | what it does |
|---|---|---|
| capture | `capture.py` | mss of the window rect (+ owned pop-ups) / PrintWindow when hidden; per-monitor DPI; block-diff change detection |
| see | `uia_source.py` `candidates.py` `icon_memory.py` | accessibility tree (read-only snapshot) + CV shapes/icons + Tesseract text (cuts at ink gaps, both polarities) + closed-outline buttons/fields/checkboxes + remembered icons |
| name | `labeler.py` `vlm.py` `grounding.py` | Set-of-Mark contact sheets: <=20 crops per picture, answer = `number: name` lines under a GBNF grammar (~6 tokens/control). Boxes use a MEASURED CoordMap (Qwen3-VL = 0..1000 grid) |
| structure | `regions.py` | background-colour bands -> title bar / menu bar / tab strip / ribbon / tool strip / status bar / canvas; ribbon split into CAPTIONED GROUPS at divider lines |
| prove | `coverage.py` `sweeper.py` | pixel audit: ink nobody claimed -> re-probe -> named control or remembered decoration; `exhausted` only when nothing control-sized is left |
| know | `knowledge/` | Atlas UI maps (path, shortcut, what it opens) + `repo_graph` (label -> code -> side effects) framed in the seven divisions (`data/divisions.json`) |
| teach | `teacher.py` `brain.py` `pointing.py` | numbered inventory -> element ids (never raw coordinates); id vs label check repairs mis-numbering; `find` for controls inside closed menus |
| show | `overlay.py` `overlay_render.py` | per-actor layered windows: click-through, no activate, excluded from capture, per-pixel alpha, 60 fps pointer |
| speak/hear | `voice_out.py` `voice_in.py` | Kokoro (optional pkg) or Windows SAPI; push-to-talk by polling Ctrl+Alt; faster-whisper / vosk (optional) or Windows System.Speech |
| run | `lesson_runner.py` `session.py` | point + speak, wait for YOUR click/"next", rescan only what changed, verify `expect`; first look is `quick`, naming upgrades in the background |

## Laws of this layer
1. **Never act for the learner.** Teaching (`ask`, `here`, `listen`) sends no click, key or text to the target app. The overlay is click-through and never takes focus. The ONLY input path in the
   package is `effectors.py` (probing / executing), closed by default: it needs `allow_input` AND (a window the Professor launched OR one you explicitly `--authorize`), it is headless (window messages / UI Automation, never
   the physical mouse or keyboard), and it hands the foreground back to you if the target takes it.
2. **Pointing comes from measured boxes.** The model cites ids; coordinates are never invented. A loose pixel snaps to the control under it.
3. **Generation is the expensive part on this GPU** (RTX 3050 6 GB: ~8 s per located control). Enumerate with CV, NAME with the model, re-check leftovers.
4. **Honest coverage.** `ScreenModel.coverage` carries ink explained, unexplained shapes and `exhausted`; `tiers_used` / `tiers_skipped` say what ran.
5. **Facts are sourced.** Explanations are built from stored measurements (`knowledge/explain.py`); the model rephrases, it does not recall features.
6. **One resident model.** `Brain` uses the vision server for text when it is up; Ollama only when it is down (`HOJAIGA_PROF_BRAIN=fastest` times both).
7. **Voice and models are optional rungs**, reported in `status`; typed questions always work.

## Model choice
Default: Qwen3-VL-8B-Instruct Q4_K_M + mmproj (already on disk; native 0..1000 boxes, strong OCR/grounding). GUI-grounding specialists exist (Duvo Eye, KV-Ground-8B,
GUI-Owl-1.5, UI-Venus-1.5, Holo2); none has a confirmed llama.cpp GGUF build yet. Drop one in with `HOJAIGA_PROF_GGUF/MMPROJ/COORD` - the calibration scene measures its
coordinate convention, nothing else changes.

## Known limits (measured, do not re-learn)
* Icon-only controls in apps with no accessibility tree are only as well named as the 8B model reads them from a 112 px cell; unnamed ones stay `unlabeled` and are pointed at by position + neighbours.
* Menus that are not open cannot be seen: the lesson says what to open and grounds the next step after the learner opens it (rescan).
* `sounddevice`, `faster-whisper`, `kokoro-onnx` are not installed: recording uses winmm, speech-to-text Windows dictation, speech SAPI.
* The source-graph needs a repository on disk; for closed-source apps only the Atlas maps and screen evidence are used.

## Open (honest)
* Dense editors (Blender, IDEs): controls are found and named, but SECTIONS come out as many small `toolbar` fragments instead of named editors (Outliner, Properties, Timeline).
  Next step: merge fragments by shared background panel + header caption, then name each panel once with the model.
* Naming budget: ~2 s per icon at 4 tok/s; a 150-icon UI needs several minutes the first time (icon memory makes every later scan of the same icons free).
* The overlay test shows a pointer in a screen corner for ~2 s; live scans of the user's real apps are only run when asked (feedback_no_focus_theft_scans).

## Second pass (same day): the six requested changes
1. **Structure** - `panels.py` finds editor areas from the picture by recursive full-span dividers (a divider must differ from the AREAS on both sides; blank gaps and grid lines are not dividers) and
   names each area once with ONE model call (contact sheet of areas) instead of one call per icon. `uia_source.py` now builds a HIERARCHY from the accessibility tree (named panes / groups / lists as
   nested regions with parents; `ScreenModel.region_path()` -> "Properties > Transform"). Blender has no tree (measured), so it uses the pixel path: areas "3D Viewport", "Outliner", "Properties Editor".
2. **Naming cost** - names, help text and shortcuts come from the tree first (22 controls + 7 regions in 111 ms, 0.4 ms in the unit test) and classic Win32 menus are read without opening
   (`native_menu.py`: 10 items with shortcuts/states in 0.3 ms). A control the tree or a menu names never reaches the vision model. Remaining icons are named from contact sheets (~16 s per sheet of 18 after `server tune`).
3. **No focus theft** - background capture ladder in `capture.grab_window`: Windows.Graphics.Capture first for windows that are on screen but covered, `PrintWindow(PW_RENDERFULLCONTENT)` first for parked/hidden windows
   (MEASURED: WGC returns the compositor's stale picture with black children for a parked window; PrintWindow forces the repaint), the other as fallback; non-DPI-aware windows are rescaled; PrintWindow's origin is
   GetWindowRect's corner (it was off by the invisible border). PL5 asserts the foreground window never changes: vision-only recall vs the tree = 21/21.
4. **The "sub-divisions of hojaiga system" file** - searched by name (any case/hyphen/trailing space/extension) in the project, architecture folders, Downloads, Documents, Desktop and OneDrive: NOT on disk.
   `divisions.find_subdivisions_file()` / `adopt_document(path)` (md/txt/html/docx/pdf) turn it into THE frame the moment it exists; until then the seven layer folders are the frame. The manual route is built:
   `knowledge/manual_rag.py` ingests a user manual (path or a URL YOU name), chunks by heading, maps every chunk onto the layers, retrieves with citations (BM25 + embeddings), and REWRITES a failed query with the
   language model (agentic). Excerpts enter the lesson prompt; a control's explanation quotes the manual only when the passage mentions it.
5. **Roles** - `session.components()["roles"]`: reasoner = language model (the resident Qwen3-VL answers text too), grounder/namer = vision model, structure = tree or pixel layout, knowledge = manual + maps + frame.
   Reasoning is already text-side; the vision model only locates and names. A smaller vision-only model can replace it via HOJAIGA_PROF_GGUF/MMPROJ/COORD without code changes.
6. **Voice** - `setup_audio.py` (`hojaiga_professor.py setup-audio [--download]`) installed and verified faster-whisper, piper-tts, kokoro-onnx, sounddevice, soundfile (pins untouched). MEASURED: Piper speaks at
   RTF 0.06 (16x faster than real time) -> default voice; Kokoro RTF 3.3-4 on this CPU -> opt-in (HOJAIGA_TTS=kokoro); faster-whisper transcribes a spoken sentence exactly in 0.8 s; the microphone path is
   sounddevice. SAPI/winmm remain only as fallbacks.
OmniParser's icon detector as another candidate source: built in Part 1b (below), because a measured recall gap appeared on UIA-blind editors (it adds nothing where a tree exists).

**Input gate (law 1):** `Effector` refuses everything unless `allow_input` AND (`owned` OR `authorized`); no SendInput, no physical mouse / keyboard; UIA patterns run on a worker thread with a deadline (a handler that opens a modal dialog blocks the call, measured).
CLI: `probe` / `exec` are dry runs unless `--allow-input --authorize`.

**Focus (measured, not assumed):** on the WinForms fixture a UIA Invoke or Select - and once even a posted tab click - made the application take the foreground (3 of 18 randomized trials; posted toolbar click and BM_CLICK
never did; an idle control run never did). Every `Effector` delivery is therefore wrapped in a focus guard: if the target's process took the foreground it is handed straight back to the user's window with the repo's own
primitive (`headless_input._hand_back_focus`, AttachThreadInput, no input synthesised), and never when the foreground moved to some OTHER process (that was the user). PL8 asserts the fixture is not left holding the
foreground, that it returned to the window the user had, and that it held it only in blips (sampled every 40 ms for the whole session). Dialog-opening verbs are not probed at all: a dialog takes the focus by itself.

**Hover tooltips (measured, honest):** the hover tier exists (`harvest.hover_tooltips`, posted WM_MOUSEMOVE to the exact child, gated to owned windows) but read 0 of 3 tooltips on the parked WinForms toolbar - frameworks show
tooltips from a real hover timer, and UIA HelpText is empty there. It is not relied on; tooltips come from HelpText / Atlas maps / label strings. A physical hover would be the only way and is refused by design.

**Hardware split (measured on this RTX 3050 6 GB / 32 GB laptop):** Ollama `qwen2.5:7b` CPU-only (`num_gpu=0`) generates 7.8 tok/s but reads prompts at 32 tok/s (default offload: 397 tok/s) - a 1-2k-token lesson prompt would
take 30-60 s on the CPU. The resident Qwen3-VL-8B (ngl 28, ~13 tok/s, already holds the context) stays the brain; Ollama stays the fallback. `networkx` holds the state graph; the overlay stays native layered windows
(PyQt6 is not installed and would add nothing); torch is a CPU build.

## Part 1b (2026-10-10): the USER GUIDE as knowledge - find it, read it, map it onto the live UI, perform it, remember it
The idea (user): the knowledge an automation needs about "how this app is supposed to work" is the app's own user guide; fetch it just in time (never one giant file), let the system use several
commands together to reach a goal, and let it teach itself - and for apps with no guide, fall back on what it learnt from the others. It is the agentic-RAG + action-chunking design, and it slots into the
existing architecture as three new boxes (marked NEW) - nothing else moved:
```
PERCEIVE  harvest (menus / tree / tooltips -> Catalog)   archetype (kind of software)   [NEW] guide_finder: install folder -> pages you name -> web (opt-in) -> manual index (chunks + citations)
          OmniParser icon detector (optional rung, UIA-blind apps only)                  capture / candidates / labeler / fusion / coverage (unchanged)
THINK     teacher prompt = KIND OF SOFTWARE + HOTKEYS + OBSERVED BEHAVIOUR + MANUAL EXCERPTS (cited) + [NEW] VERIFIED WORKFLOWS (skills)
          [NEW] guide_steps: manual prose -> steps (menu paths, chords, typed text, check boxes) -> grounded in the live Catalog (unknown terms reported, never forced)
ACT       executor plan order: skill -> words -> GUIDE -> other apps' skills of the same kind (hypotheses) -> model;  route ladder value > command > shortcut > control > posted click;
          every step verified by a delta;  [NEW] skills: only fully verified runs are remembered (macro-action library), retired after 3 failures or when a verb vanishes;  achieve() self-heals
```
| piece | module | behaviour (all enforced + tested) |
|---|---|---|
| guide discovery | `knowledge/guide_finder.py` | tier 0 already indexed -> tier 1 the application's own install folder (Help/docs/manual files: md html txt docx **pdf**; licences, plugins, vendored dirs, huge files skipped; chm reported not read; **shared folders like System32 / Program Files / a folder with 60+ executables are never searched**) -> tier 2 pages YOU name (`guide fetch --url`) -> tier 3 web search, **OFF unless `HOJAIGA_GUIDE_WEB=1` / `--web`**. Web policy: robots.txt honoured (unreadable = do not fetch), same host + doc path only, page / depth / byte / time caps, delay between requests, no private or loopback addresses, text / html / markdown / pdf only, every request logged (`data/professor/logs/guide_fetch.log`), results ranked vendor-docs first (social / video / shop / Q&A dropped), custom search endpoint `HOJAIGA_GUIDE_SEARCH_URL` (e.g. local SearXNG). Only chunks + citations are kept locally. |
| reading | `knowledge/manual_rag.py` | HTML now keeps numbered steps, list items, tables and the **bold / kbd** interface terms; chunks keep their LINES (a procedure stays a list) |
| manual -> UI | `knowledge/guide_steps.py` | rules only: numbered steps, "To X, click Y." purpose sentences, "You can simply ...", compound sentences, `File > Export > PDF` paths, `Ctrl+B` chords, `Type "..." in the Title field`, "Tick the ... checkbox"; grounding: exact path > label > word overlap; a chord only if the application prints it; a procedure that is less than 60 % grounded is refused |
| skills | `skills.py` | compile only from a run where EVERY step was verified; same chain under another wording = one skill with aliases; found by goal similarity; typed text kept as a slot (a quoted string in the next goal rebinds it); safety recomputed from the CURRENT catalog; cross-application suggestions (same archetype, every step resolves) are hypotheses that become native skills only after they verify |
| executor | `executor.py` | text goes into a named field headlessly (UIA ValuePattern); a check box already in the wanted state is left alone; **a plan whose only link to the request is one shared word is refused** ("remove every marker" must not become "Add Marker" - found by PL10 and fixed) |
| icon detector | `icon_detector.py` | MEASURED: Blender (UIA-blind) 195-275 candidates, detector 0.8 s warm on the CPU, +28 real controls (selection-mode, shading and transport buttons, header carets, outliner visibility icons); nothing added on the synthetic app (CV 45/45) -> optional rung, only where the tree has < 15 controls, `HOJAIGA_PROF_YOLO=0` switches it off |
CLI: `guide find|fetch|status`, `skills list|show|forget`, `exec` now plans with skills + the guide and learns from verified `--run`s (`--no-learn`).

**Measured on the live Atlas fixture (PL10, parked, headless):** goals in the MANUAL's words - "place a marker" and "remove every marker" - were planned from the indexed guide (cited), performed and checked against the
fixture's own state label (markers 0 -> 1 -> 0), remembered, then replayed from the skills (1 -> 0); "delete the shapes" came from the guide too and WAITED for a human (shapes untouched); a guide term with no control

grounding, skill lifecycle, the whole loop on a fake application.

**Honest limits:** a guide describes ONE version in prose; the Professor treats it as a hypothesis and trusts only what verifies on the screen. "Every app in the world" is not promised: the report says exactly which tier found
what (`guide status`), and an app with no findable guide falls back to the archetype memory + probing. Web retrieval was tested against a local doc server and canned search pages, NOT against the live internet (no
live web fetch was run). `.chm` help, scanned PDFs (no text layer), prose with no imperative steps, and steps that must drag or draw are not turned into plans. A manual that is split across two chunks mid-procedure
is read one chunk at a time. Part 2 (interaction / training) is still to come from you.

## Part 3 (2026-10-10): the ML models, the guide CORPUS, and running a guide against the REAL application (app-run harness)

## Part 7 (2026-10-11) - the VIRTUAL MOUSE: every mouse verb, any application the run launched, the person's cursor never used
User: "the virtual mouse is one of the most important things of this system ... implement flicks, dragging, selecting, drag select, drag-drop, all the functionalities a physical mouse owns ... we don't want the user to lose control over the physical cursor".
- `professor/pointer.py` - `VirtualPointer`: hover, click (L/R/M/X1/X2, x1-x3), double / triple click, hold, drag (any button, any path), stroke, drag-select (marquee), lasso, flick, drag-and-drop (OLE), wheel (both axes), Shift/Ctrl/Alt held. Every verb is COMPILED to an event script (`Ev`: move/down/up/wheel + time + modifiers; `s_click`, `s_drag`, `s_drop`, ...) that no route knows about; a ROUTE delivers the script. Routes (order LEARNED per application, `app_traits.json` key `pointer`): `native` (adapter `.pointer_events`) > `posted` (window messages to the child under the point, DPI-correct, double-click message only for classes with CS_DBLCLKS) > `shim` > `uia` (plain wheel via ScrollPattern) > `touch` (ghost window). The Effector's `click_xy` / `pointer_gesture` and the gesture driver all go through the same object.
- `professor/inproc/agent.js` + `InprocAgent` (Frida 17.23.3, pip, wxWindows licence 3.1, local, no telemetry; lazy import, absent -> route `unavailable`): loaded ONLY into a process the run launched (`fx.owned`). Answers the application's POLLING of the mouse with the virtual pointer's state: GetCursorPos / GetPhysicalCursorPos / GetCursorInfo / GetMessagePos / GetAsyncKeyState / GetKeyState / GetKeyboardState, WindowFromPoint at the virtual point (answers with the child under the pointer), and rewrites `MSG.pt` of dequeued mouse messages (client -> screen exactly as the system would: OLE's drag loop reads it). GUARD: SetCursorPos / SetPhysicalCursorPos / ClipCursor / mouse_event / mouse SendInput are SWALLOWED in that process (a 3D editor wrapping the pointer during a drag can no longer move the person's cursor); self-tested at attach (the process is asked to move the cursor, the agent must answer the call itself). `quiet()` keeps the virtual state until the application stopped polling (it drains its queue later than we post).
- `GhostWindow` + `TouchRoute`: for POINTER-AWARE toolkits only (window classes WinUI / Microsoft.UI / Windows.UI / DesktopChildSiteBridge / ApplicationFrame / Xaml: `pointer_aware()`): the owned window is shown for the length of the gesture at alpha 2/255 (layered), never activated, topmost, on the side of the screen away from the person's cursor, only when the person has been idle >1.2 s (visible mode exempt); synthetic touch is injected; window put back (position re-checked: an application may answer the move with a DPI re-layout). Touch is NOT tried on other toolkits (measured: WinForms and WPF promote touch to mouse and move the cursor 880-1500 px - a first measurement would itself be a violation); if it ever moves the cursor (attributed only when no real input arrived) the cursor is put back and the route closed. `CursorWatch` samples GetCursorPos every 3 ms during every delivery; `real_input_seen` (GetLastInputInfo) tells the person's own movement from the route's.
- LEARNING POLICY (a bug found live and fixed): a route is recorded as `ignored` only by CONTRAST (a later route produced the effect the earlier one did not, twice), never because a gesture changed nothing - the first version persisted 'ignored' for posted+shim+touch after two no-op gestures on Paint and then had NO route left. `note_ineffective` demotes a route for the session only; an empty ladder says why (`why_no_route`). Legacy facts (`posted_pointer`, `touch_moves_cursor`) are honoured by `load_traits`.
- Surfaces: `gestures.free_rect` - when the tree does not name the canvas, the largest block of the window no control covers (a 32x30 'pane' was once taken for Paint's canvas); `surface_of` prefers a real node only if it is >=12% of the window.
- MEASURED (2026-10-11, lab targets in `professor/lab/`, compiled with the .NET Framework csc.exe, parked at -20000; `lab_matrix.py`, `blender_matrix.py`): WinForms (DPI-unaware and aware): all 10 verbs by `posted`, drop needs `shim`; WPF: posted = 0 events for everything; with the agent: hover, L/R/M click, double, drag, flick, drop OK, **wheel NOT delivered** (posted or shim; WPF rejects it for a reason not found; the `uia` route is its fallback where a control has a ScrollPattern); Blender 5.2 (GHOST/OpenGL; no `event_simulate` in this build): click-select, shift-click extend, deselect, drag-select box, middle-drag orbit, shift+middle pan, wheel zoom in/out, right click - all verified by Blender's own state through the bridge; cursor never moved in any of it. - Pitfalls: WPF checks WindowFromPoint / GetCursorPos before it accepts a mouse message; OLE DoDragDrop takes the pointer from MSG.pt (a posted message carries no real one); a window parked at -37500 breaks 16-bit message coordinates (parking is -24000); `taskkill /IM` kills every instance incl. the person's - kill by PID only; a heredoc collapses `\\n` in generated patch files (write patch scripts with the Write tool).
