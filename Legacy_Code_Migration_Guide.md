\# Legacy Reference Guide

Version: 1.0

\---

\# Purpose

The attached legacy automation project is reference material only.

It must never dictate the new architecture.

Its purpose is to provide reusable implementations, algorithms and engineering solutions.

\---

\# Primary Objective

Mine reusable knowledge.

Refactor reusable components.

Discard obsolete architecture.

Never redesign the new architecture around the old implementation.

\---

\# What SHOULD be reused

\- Stable algorithms  
\- Browser automation  
\- Playwright logic  
\- CDP implementations  
\- Window handling  
\- File management  
\- Logging  
\- Reports  
\- Retry mechanisms  
\- Validators  
\- Utilities  
\- Configuration loading  
\- Database access  
\- Plugin loading  
\- Download management  
\- Upload management  
\- Browser profiles  
\- Sandbox implementations  
\- Testing utilities

\---

\# What SHOULD NOT be reused

\- Project structure  
\- Controller hierarchy  
\- Old routing  
\- Old architecture  
\- Global state  
\- Tight coupling  
\- Hard coded paths  
\- Duplicate implementations

\---

\# Evaluation Process

For every legacy file

1\. Understand its purpose.  
2\. Identify reusable logic.  
3\. Compare against new architecture.  
4\. Refactor if beneficial.  
5\. Discard if obsolete.

\---

\# Migration Rules

Never copy entire folders.

Never duplicate functionality.

Extract reusable components.

Reorganize according to the new organ.

\---

\# Folder Classification

Each legacy file should be classified as

REUSE

REFactor

REPLACE

ARCHIVE

DELETE

\---

\# Documentation

Every reused component must include

Original Location

New Location

Reason for Migration

Required Modifications

Compatibility Notes

\---

\# Coding Rules

Prefer composition.

Prefer dependency injection.

Prefer modularity.

Keep public interfaces stable.

Avoid global variables.

Avoid duplicated logic.
